# 基于 Hadoop 与 XGBoost 的生鲜仓储传感器记录损耗预测系统的设计与实现

## 摘要

针对冷库管理中传感器数据分散、人工巡检难以及时识别高风险记录的问题，本项目设计并实现了一套生鲜仓储传感器记录损耗预测原型系统。系统采用 Mendeley Data 公开的冷库传感器记录数据，完成原始 CSV 的字段校验、数值范围检查和 Good/Bad 标签标准化；在模型实验中使用训练集互信息得分进行特征筛选，并按互信息得分对保留特征进行缩放，分别训练原始 XGBoost 和加权 XGBoost 二分类模型；在 Web 端使用 Spring Boot、SQLite 和静态页面完成记录浏览、风险预测、预警记录和实验指标展示。

数据集包含 10995 条有效记录，字段为水果类别、温度、湿度、光照、二氧化碳和损耗标签。实验固定随机种子为 20261122，采用 8:2 分层划分。原始模型测试集 Accuracy 为 0.999090，加权模型为 0.998636；加权模型 Recall 为 1.000000，ROC-AUC 为 0.999998。结果表明，该实现可以完成从清洗数据到 Web 预警的联动，但当前数据不含时间戳，因此研究结论仅适用于传感器记录分类，不应扩展为严格的时间序列预测。HDFS 实机运行、Windows x64 原生打包和离线验收尚未完成。

**关键词：** 冷库传感器记录；Hadoop；互信息；XGBoost；风险预警

## ABSTRACT

This project designs and implements a prototype for spoilage-risk prediction from cold-storage sensor records. The system validates and cleans a public Mendeley CSV dataset, computes mutual information on the training split, scales selected features with mutual-information weights, and compares a baseline XGBoost classifier with the weighted classifier. A Spring Boot and SQLite service provides record browsing, prediction, alert persistence, and experiment-result views. The dataset contains no timestamp, so the work is described as classification of sensor records rather than strict time-series forecasting. Hadoop execution on a real HDFS environment and native Windows x64 packaging remain to be verified.

**Key words:** cold-storage sensor records; Hadoop; mutual information; XGBoost; risk alert

## 第1章 绪论

### 1.1 研究背景

冷库中的温度、湿度、光照和二氧化碳等环境因素会影响生鲜货品的保存状态。传统管理方式主要依靠人工查看和经验判断，传感器数据虽然能够持续采集，但如果没有清洗、分析和可视化环节，数据难以直接服务于仓储决策。大数据处理、特征工程和集成学习可以为低成本的风险识别原型提供技术基础。

### 1.2 研究内容

本项目的工作包括四部分：第一，固定公开数据来源并完成字段、缺失值、数值范围和标签检查；第二，使用 Hadoop/HDFS 设计可复现的数据处理链路；第三，在训练集上计算互信息，完成特征筛选与加权 XGBoost 对比实验；第四，开发 Spring Boot、SQLite 和静态 Web 组成的业务原型，保存预测记录和预警状态。

### 1.3 论文结构

全文共六章。第一章介绍背景和研究内容；第二章分析需求并给出总体设计；第三章说明数据处理、互信息和模型实验；第四章说明后端、数据库和前端实现；第五章汇总测试和实际指标；第六章总结已完成工作并说明限制。

## 第2章 需求分析与总体设计

### 2.1 用户与业务需求

系统面向冷库管理人员，核心流程是查看传感器记录、提交一条记录进行风险预测、查看风险概率和预警记录。系统还需要保留实验指标，便于论文中的结果追溯。由于数据集只有 Good/Bad 标签，系统的“损耗风险”表示分类风险，不表示具体损耗百分比。

### 2.2 功能需求

1. 数据记录：保存水果类别、温度、湿度、光照、二氧化碳和来源说明。  
2. 风险预测：调用加权 XGBoost，返回 Good/Bad、风险概率和模型版本。  
3. 预警管理：当标签为 Bad 或风险概率不低于 0.5 时生成 HIGH 预警。  
4. 实验展示：读取基线模型和加权模型的指标。  
5. 运行管理：提供健康检查、启动和停止入口，并对模型缺失和输入错误给出错误提示。

### 2.3 总体架构

系统分为数据层、算法层、服务层和展示层。数据层保存原始 CSV、清洗 CSV、字段 Schema 和清洗报告；算法层负责互信息和 XGBoost；服务层由 Spring Boot 和 SQLite 组成；展示层为静态 HTML、CSS 和 JavaScript。Hadoop/HDFS 位于离线数据处理链路中，当前仅完成脚本，未宣称真实集群验证。

## 第3章 数据处理与互信息加权 XGBoost 模型

### 3.1 数据来源与字段

数据来源为 Mendeley Data 数据集 `czz68d9fwj/1`，DOI 为 `10.17632/czz68d9fwj.1`，许可证为 CC BY 4.0。原始字段名称包含 `Fruit`、`Temp`、`Humid (%)`、`Light (Fux)`、`CO2 (pmm)` 和 `Class`。ETL 后统一为 `fruit`、`temp`、`humid`、`light`、`co2`、`label` 和 `label_name`。数据没有时间戳，清洗报告记录了这一事实。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| fruit | 类别 | Orange、Pineapple、Banana、Tomato |
| temp | 数值 | 摄氏温度 |
| humid | 数值 | 相对湿度百分比 |
| light | 数值 | 光照强度 |
| co2 | 数值 | 二氧化碳浓度 |
| label | 0/1 | Good=0，Bad=1 |

清洗脚本读取 10995 条记录并输出 10995 条记录。当前报告中的样本分布为 Good 5667 条、Bad 5328 条；这只是数据集标签分布，不是现实仓储损耗率。

### 3.2 Hadoop 数据处理设计

HDFS 脚本提供创建目录、上传原始文件、下载结果和调用清洗脚本的步骤。由于当前开发机未运行 Hadoop/HDFS，论文只记录脚本设计和未验证状态，不把脚本存在写成 Hadoop 集群运行成功。后续补验时应记录 Hadoop 版本、NameNode/DataNode 状态、输入输出路径和运行日志。

### 3.3 互信息特征筛选与加权

训练集经过独热编码和标准化后计算互信息。以训练集互信息中位数作为筛选阈值，至少保留一个特征。对保留特征 j，权重定义为：

`w_j = (MI_j + 10^-6) / (mean(MI) + 10^-6)`

加权模型使用 `x'_j = x_j × w_j` 作为输入。互信息只由训练集计算，测试集只用于最终评价，避免数据泄漏。

本次实验保留了 `fruit=Tomato`、`temp`、`humid`、`light` 和 `co2`。其中 `light` 权重约为 1.945，`humid` 权重约为 1.195，`temp` 权重约为 1.051，`co2` 权重约为 0.796。

### 3.4 模型实验

实验固定随机种子 20261122，测试集比例为 0.2，使用原始 XGBoost 作为基线。分类指标为主，MSE、MAE 和 R² 用于描述概率输出与 0/1 标签的误差。

| 模型 | Accuracy | Precision | Recall | F1 | ROC-AUC | MSE | MAE | R² |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 原始 XGBoost | 0.999090 | 0.999062 | 0.999062 | 0.999062 | 0.999997 | 0.000801 | 0.004032 | 0.996794 |
| 互信息加权 XGBoost | 0.998636 | 0.997194 | 1.000000 | 0.998595 | 0.999998 | 0.001130 | 0.005502 | 0.995476 |

从当前固定实验看，加权模型的 Recall 和 ROC-AUC 略高，但 Accuracy、F1、MSE、MAE 和 R² 不优于基线。因此不能笼统声称加权模型全面提升性能；后续可以补充多次随机种子、交叉验证和更严格的特征选择对比。

## 第4章 系统详细设计与实现

### 4.1 Spring Boot 后端

后端使用 REST 接口接收和返回 JSON。`/api/health` 用于健康检查，`/api/records` 用于记录读写，`/api/predict` 调用模型运行器，`/api/predictions` 和 `/api/alerts` 返回历史结果，`/api/experiments` 返回实验指标。模型运行器采用标准输入输出协议，后端不在模型不可用时生成假结果，而是返回 `MODEL_UNAVAILABLE`。

### 4.2 SQLite 持久化

应用启动时初始化四张表。预测流程先保存传感器记录，再调用模型，最后保存预测和预警。当前已验证预测记录可以写入 SQLite，并能通过查询接口读取。数据库目录由 `M09_DB_PATH` 控制。

### 4.3 Web 页面

静态前端提供总览、传感器记录、风险预测、预警记录和模型指标区域，页面通过 `/api` 获取数据。接口不可用时显示错误信息，不内置测试假数据。正式论文需要补充四张来自真实程序运行的不同功能截图；当前仓库尚未形成截图证据。

本项目完成了公开冷库传感器记录的清洗、互信息特征工程、原始与加权 XGBoost 对比、Spring Boot 与 SQLite 后端以及静态 Web 预警页面。实际联调证明，系统能够保存记录、调用模型和生成预警。当前结果说明加权策略在 Recall 和 ROC-AUC 上有一定表现，但没有全面超过基线。
